## 核查与设计依据

第一版实际是受限的配置编辑器：头像、分类、系列数组被锁定；头像上传、favicon 生成与登记没有串联；二维码显示内部文件名；分类的 `foil` 只读，前台还没有消费该预设；所有条目全展开，形成很长的表单。以上缺口已通过专门的新增流程与界面调整修正；通用配置编辑仍保护稳定 ID 和执行表达式。

- [Carbon 数据列表](https://carbondesignsystem.com/components/data-table/usage/)：搜索与主要动作置于列表工具栏；列表用于选择，复杂编辑进入独立面板。采用摘要列表与单项编辑，避免展开全部字段。
- [GOV.UK 错误反馈](https://design-system.service.gov.uk/components/error-summary/)：错误不能只靠颜色；保留输入并提供可读反馈。继续保留版本冲突保护，表单使用原生标签、下拉框、复选框。
- [Pokémon Cards CSS Holographic Effect](https://poke-holo.simey.me/)：研究渐变叠层、混合模式和指针位置驱动反光的方法。使用本站自己的低饱和渐变，不引入宝可梦素材；编辑器和前台共享光泽样式，提供静态键盘预览，减少动态时关闭指针跟随。
- [Sharp 输出接口](https://sharp.pixelplumbing.com/api-output/)：头像输出 WebP，派生本地 PNG favicon；二维码采用无损 WebP，保留清晰边缘；上传先验证真实格式与像素上限。

## 本轮实施顺序与验收

1. **管理界面**：统一字号、间距与按钮；列表搜索、单项编辑、清晰的新增操作；隐藏实现路径到详情；窄屏不溢出，保存状态不遮住表单。
2. **现有字段**：社交链接显示与前台相同的 SVG 图标；二维码使用图片地址和上传选择；光泽改为命名下拉菜单与实际预览。
3. **新增流程**：新增身份同时生成头像与 32/48px favicon；新增分类同时登记角色、图片、题签和分类目录；新增系列选择已有分类。已有 ID 保持稳定，新增不得覆盖文件。新增后的分类和系列不需要重启后台即可用于文章。
4. **图片归属**：本轮先闭合本地流程，自动转图后放入 `public/media/`，随 Git 部署即可使用。现有 R2 资产继续可读。R2 自动上传单独排期，不把“保存到本地”伪装成“已上传云端”。
5. **验证与文档**：隔离工作区验证新增、冲突、图片、关联；浏览器检查桌面、移动端、键盘与减少动态；运行项目构建检查，更新实际完成状态。

## R2 后续方案与边界

按用途选择输出：头像 `avatars/`、文章/资源沿用资产清单路径；本地 favicon 不上传 R2。优先复用已有 rclone 凭证，通过服务端受限参数调用单文件 `copyto`，不接受任意远程路径或命令。流程为处理 → 展示文件/目标 → 上传 → 验证对象 → 保存引用；上传失败不写入 CDN 地址。对象采用内容哈希避免覆盖，允许重试；清理孤立对象和删除已有内容独立审查。不要用现有整目录 R2 同步脚本替代单次上传。

`copyto` 默认可以覆盖同名目标，不能仅凭命令名宣称安全。后续实现应要求输入确为文件，使用固定目标前缀、内容哈希和 `--immutable`，并核对上传结果；不把 `--ignore-existing` 的跳过结果当作上传验证成功。[rclone 官方说明](https://rclone.org/commands/rclone_copyto/)

当前没有完整 R2 上传、删除、回滚及云端身份系统。本地新图片也不会因保存自动 push；发布仍使用 Git 与现有部署流程。多文件新增有版本复核和失败恢复，不能宣称跨文件写入具备数据库式原子性；断电后的恢复需要核对记录。

### 本机构建环境的区别

本轮普通 `npm run check` 首次失败的原因是 Windows Application Control 阻止 `@bruits/satteri-win32-x64-msvc` 原生模块加载，错误码为 `ERR_DLOPEN_FAILED`；不是文章内容错误，也不是缺失 MD 字段。没有关闭系统策略或更改生产依赖来解决。

为继续验证，使用相同版本的官方 `@bruits/satteri-wasm32-wasi@0.10.5`，仅安装在被忽略的 `.tmp/admin-wasi/` 下。该包声明 `cpu: wasm32`，所以隔离安装使用 npm `--force --ignore-scripts`，仅跳过包的 CPU 安装检查，不执行原生文件或关闭 Windows 策略；生产 `package.json`／锁文件未增加此依赖。通过依赖自带的 `NAPI_RS_FORCE_WASI=true` 与进程级 `NODE_PATH` 运行完整检查，结果如上，WASI 仍会输出实验性提示。

若此工作区仍保留验证目录，可在 PowerShell 的**单独终端**使用：

```powershell
$env:NODE_PATH = (Resolve-Path '.tmp/admin-wasi/node_modules').Path
$env:NAPI_RS_FORCE_WASI = 'true'
npm run check
```

同一终端运行 `npm run dev` 可使用相同后端预览；普通 `npm run admin` 不依赖该原生模块。临时目录不会提交，其他电脑不应依赖它。Windows 原生加载限制尚未解决，不能把此验收描述为“普通环境无条件构建通过”；也未据此宣称 GitHub Actions 或线上部署已经完成。
