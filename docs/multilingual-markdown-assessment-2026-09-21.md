# 单篇 Markdown 的中／英／日展示研判

日期：2026-09-21。**仅调研，未实现语言切换、翻译 API 或多语言路由。**

## 建议

可以保持一个仓库、一次部署、一套页面组件，也可以每篇文章只维护一个 Markdown。需要分别决定「译文存哪里」「如何产生译文」「如何分享某个语言版本」；这三件事不必绑定在一起。

结合目前个人博客的规模，建议优先考虑：**单文件按语言存放完整正文 + 本地辅助翻译／人工校对 + 构建时生成语言版本**。中文旧地址继续有效，英文／日文只是同一站点自动生成的 URL，不是另建两套站点。如果最在意只写中文，则改用中文源文件 + 自动生成的译文缓存。自动化可以减少排版和同步工作，不能消除翻译质量与过期校对的成本。

日语语言代码使用 `ja`，`JP` 是国家代码，不建议把语言字段命名为 `jp`。

## 主流做法与适用边界

- [Astro i18n](https://docs.astro.build/en/guides/internationalization/) 提供语言路由、链接和回退能力，不自动翻译正文。我们可以由同一篇内容在构建时产生多个页面，共用模板与资源。
- [Starlight](https://starlight.astro.build/guides/i18n/) 通常按语言目录放内容，同名文件建立对应，并支持未翻译内容的提示／回退；[Docusaurus](https://docusaurus.io/docs/i18n/introduction) 也以完整 Markdown 文档为翻译单位。这种方式工具支持成熟、上下文完整，但不符合你优先维护一个文件的习惯，因此作为最后备选。
- [remark-directive](https://github.com/remarkjs/remark-directive) 可以解析 Markdown 中的容器指令，适合我们控制写作和构建流程的项目。它只提供语法解析，语言选择、校验和输出仍要自己实现；单文件多语言并非 Astro 原生开关。
- [Google 的多语言站点建议](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites) 偏向不同语言使用各自 URL，并明确给读者切换入口。这不要求多个域名或多个部署；只靠 Cookie／浏览器语言改变同一 URL 的内容，不利于分享与检索。

## 可行方案比较

| 方案 | 作者维护内容 | 优点 | 代价与限制 |
| --- | --- | --- | --- |
| A. 单 MD，完整语言块 | 一个文件内 zh-CN／en／ja 三块 | 最符合你的偏好；图片链接、ID、日期共用；译文可审阅 | 文件约三倍长；需要自定义解析、后台编辑和过期提示 |
| B. 中文 MD + 生成译文缓存 | 只改中文；译文由本地命令生成 JSON／构建缓存 | 手工负担最低，不新增手工维护的 en／ja Markdown | API 成本、术语一致性、改稿失效与人工修订保留都要设计 |
| C. 读者浏览器翻译 | 只有中文 | 几乎没有站点维护成本，适合先试水 | 浏览器功能不一致；缺少稳定的译文分享／SEO／作者校对版本 |
| D. 独立翻译 MD | 每种语言一份正文，共用文章 ID | 生态成熟，差异比较和翻译协作简单 | 文件较多，要同步内容；仅作最终备选 |

不建议在中文、英文、日文之间逐句交错：长文编辑更碎，插入段落时容易错位，文学表达也不适合强制逐句对应。以完整文章或完整章节保留上下文更合适。

## A 方案的文件示意

以下只是拟议语法，**现在不要直接用于正式文章**：

````markdown
---
articleId: telysta-central-asian-attire
sourceLanguage: zh-CN
publishedAt: 2026-09-17
category: portraits
locales:
  zh-CN:
    title: Telysta 的中亚风格服饰
    description: ……
  en:
    title: Telysta in Central Asian-Inspired Attire
    description: ……
    status: reviewed
  ja:
    title: 中央アジア風の衣装をまとった Telysta
    description: ……
    status: machine
---

:::lang{code="zh-CN"}
## 服饰设计
中文正文……
:::

:::lang{code="en"}
## Costume Design
English text…
:::

:::lang{code="ja"}
## 衣装デザイン
日本語の本文……
:::
````

共享元数据只写一次。图片二进制只存一份，正文引用同一地址；图片说明和 alt 可按语言翻译。将正文塞进 YAML 多行字符串虽可行，但会牺牲 Markdown 编辑、预览与差异可读性，因此不建议。

构建先通过 AST 识别并提取选中语言，之后再运行标题处理、数学公式、简谱、目录及 HTML 渲染。不能用一个正则从全文截语言块，也不应该把三份正文一起渲染再简单用 CSS 隐藏：这会混入搜索、重复标题 ID、脚注及辅助阅读内容，还可能重复加载图片。

## 展示与 URL

推荐保留 `/blog/<现有路径>/` 为中文，按需生成 `/en/blog/<同一标识>/` 和 `/ja/blog/<同一标识>/`。页面上提供「中文 / English / 日本語」的原生链接，直接分享就能指向正确语言，无 JavaScript 也能使用。所有语言继续复用当前代码、配置和部署。

如果明确不要任何语言路径，也可以在单页使用 `?lang=en` 切换，或按需加载对应语言 HTML／JSON。但纯 GitHub Pages 无法在服务器根据查询参数选择静态文件；客户端方案需要处理首屏闪动、无 JS 回退、搜索和链接预览。适合作为便利阅读功能，SEO 能力不及独立静态 URL。

缺少译文时明确显示「此文暂仅有中文」，不要把中文正文标成 `lang=en`。优先采用用户主动选择；浏览器语言只能做首次建议，不强制跳转。

## B 方案与翻译服务

可新增一个主动运行的本地翻译命令：读取中文正文 → 提取可翻译文本／图片说明 → 调用服务 → 校验 Markdown 结构 → 保存待校对译文缓存。正常 `npm run build` 只消费已有缓存，不联网翻译，避免一次 push 因配额、服务超时或输出变化而失败。

[DeepL 的 HTML 翻译接口](https://developers.deepl.com/docs/translate/translating-html) 支持 HTML 标签处理和排除翻译区域，但不能据此假设原始 Markdown 中的代码、公式、链接、简谱 ID 会自动安全保留。无论使用专门翻译服务还是语言模型，都需要保护这些节点，并维护人名／服饰／宗教术语表，例如 Weiser、Telysta、Rhaelysa 不随意改名。

译文缓存应记录源内容哈希、目标语言、服务／模型版本、术语版本、生成时间及校对状态。只翻译发生变化的文章，源文修改后标记旧译文待复核，不覆盖人工修改。不要在每个访问请求上重新翻译。

如果以后做在线翻译按钮，需要独立服务端／Worker 保管密钥、鉴权或限流、费用上限和缓存。当前 GitHub Pages 静态页面不能安全保存翻译 API 密钥；直接塞进前端脚本不可取。草稿也不应默认上传给外部翻译服务。

## 本项目需要覆盖的接口与风险

1. **内容加载与校验**：目前使用 Astro Collections、自动元数据回退和 `series`／`seriesOrder` 校验。多语言应以稳定 `articleId` 代表一篇文章，不能让三个语言版本被计为三篇系列文章。
2. **Markdown 管线**：独立处理各语言的标题、脚注、公式、`score` 块和相对图片；未翻译部分有明确回退。原有单语文件继续原样工作。
3. **目录与导航**：各语言的 TOC 锚点和页面标题一致；切换语言保留文章身份，跨语言定位段落可后续再做。前后章只改变语言，不改变系列顺序。
4. **SEO 与分享**：按语言生成标题、摘要、`lang`、canonical、互相对应的 hreflang 和站点地图；不要把所有英文／日文 canonical 都指回中文。已审阅与机器翻译状态应可见。
5. **搜索与评论**：搜索按语言取正文、只返回所需版本；Giscus 当前按 pathname 关联，增加语言路径会分裂评论，需要先决定统一稳定 ID 还是各语言独立讨论，兼容已有评论。
6. **本地后台**：保存时原子更新共享字段与语言块；按语言切换编辑／预览，显示过期标记，不能丢失未知字段、代码块或用户改动。
7. **质量与工作量**：浏览器翻译可先用，但正式人物设定、文化描述、宗教观察建议人工校对。三种语言意味着三份表达内容，一份文件并不能免去内容校对，只是减少文件组织成本。

## 建议的后续试点

先选一篇短人物介绍与一篇含图片／代码／简谱的长文做 A 方案验证；保留现有路由，暂不迁移全部文章。确认编辑体验后，再增加 B 的辅助翻译和哈希失效提示。验收覆盖中／英／日切换、刷新／分享、无 JS、缺译回退、正文目录、系列排序、评论身份、后台保存和不依赖翻译网络的生产构建。

本次只补齐现有 `titleEn`／`descriptionEn`，不代表已经具备全文英文或日文版本。
